# Аудит полноты реализации и восстановления контекста

Дата: 2026-09-06. Пакет: `vibe-kmp-skills 2.2.0`, Protocol 2.0. Проверенный HEAD: `0bfc4d9410cb641f6be261c75bd49cf7d17e6200`.

Проверены инструкции 15 skills в части delivery/recovery, общие контракты, исполняющие скрипты и профильные тесты. Установленные `vibe-developer` и `vibe-acceptance-auditor` являются Junction на этот репозиторий. Это аудит механизма skills, а не closure-аудит конкретного приложения: он не присваивает приложению PASS/GAPS/BLOCKED. Реализация skills не изменялась.

## Вывод

Архитектура контроля полноты сильная: есть атомарные обязательства, сохранённое состояние, привязанные к версии кода доказательства, независимый аудит и отдельные признаки готовности реализации и релиза. Защита от потери контекста предусмотрена явно, включая специалистов и прямые задания.

Однако исполняемый протокол слабее описанного. Обнаружены воспроизводимые случаи потери незавершённого состояния и ложного допуска завершения. Восстановление после сжатия остаётся добровольно исполняемой инструкцией агента; механизм не гарантирует, что агент запустит восстановление и что всё существенное было сохранено до сжатия. Автоматическая проверка полноты прозы также не заменяет содержательный аудит.

## Что уже работает хорошо

- **Декомпозиция спеки.** AppSpec 2.0 требует связь requirement → отдельные AC, Given/When/Then для каждого AC, зависимости без циклов, явные решения по CRUD и доменным операциям, платформенные и repository/release gates. `should` и `could` не разрешают забыть утверждённое требование. Исключение задаётся явно. См. [app-spec-contract.md](../vibe-developer/references/app-spec-contract.md).
- **Доказательства по каждой поверхности проверки.** Закрытие должно учитывать production/test evidence, текущий результат команды, обязательные UI/platform/component surfaces, а не только наличие файла или успешную сборку. Последующий FAIL нельзя спрятать, исключив ссылку из ledger: валидатор сканирует каталог receipts. См. [validate-delivery-ledger.py](../vibe-developer/scripts/validate-delivery-ledger.py).
- **Независимая финальная проверка.** Аудитор получает новый ephemeral CLI-процесс, сначала читает AppSpec, затем сравнивает свой inventory с ledger. Launcher записывает событие создания задачи и метаданные запуска. После исправлений нужен новый audit request. Финальная проверка идёт после аудита; отчёты проверяются на соответствие JSON. См. [SKILL.md аудитора](../vibe-acceptance-auditor/SKILL.md).
- **Состояние вынесено из разговора.** Ledger, immutable hand-offs, receipts, recovery packets, сохранённые пользовательские решения и точный next action позволяют восстановиться без истории чата. Запись ledger защищена блокировкой, digest и атомарной заменой.
- **Осторожное восстановление.** `resume-delivery.py` различает clean, expected/unexpected drift и stale evidence; возвращает активный AC/gate, незакрытые обязательства, проверки, блокеры, решения и hand-offs. Изменение спеки проходит через reconciliation с сохранением истории. Все 13 реализационных специалистов имеют recovery-инструкции, включая прямые задания.

## Подтверждённые дефекты

### F1 — P1: финальный валидатор пропускает непринятый hand-off с блокером

**Источник:** [validate-delivery-ledger.py](../vibe-developer/scripts/validate-delivery-ledger.py), строки 148–158 и 282–283; [resume-delivery.py](../vibe-developer/scripts/resume-delivery.py), обработка pending hand-offs.

Финальный валидатор проверяет только hand-offs, уже перечисленные в `ingestedHandoffs`. Он не сравнивает эту коллекцию со всеми файлами `.vibe/handoffs`, хотя SKILL прямо запрещает завершать работу с непроверенным hand-off.

**Воспроизведение:** к положительной closure-фикстуре добавлен корректный, текущий, ещё не принятый hand-off с `blockers: ["A failure branch is still missing"]`. Итоговый валидатор вернул `implementationComplete=true`, `releaseReady=true`, `errors=[]`. При этом resume правильно вернул `completionEligible=false` и обнаружил pending hand-off.

**Последствие:** разные точки входа дают противоположный ответ о готовности; последний возврат специалиста может остаться непрочитанным при объявлении завершения.

**Исправление:** вынести проверку незавершённых hand-offs в общий валидируемый инвариант и применять перед audit request и финальным результатом. Проверять также незавершённые назначения/recovery packets. Устаревшие материалы закрывать явным disposition с историей, чтобы не создавать вечный блокер.

### F2 — P1: specialist checkpoint забывает старые pending checks и blockers

**Источник:** [specialist-state.py](../vibe-developer/scripts/specialist-state.py), строки 18–23 и 30–41.

Новый packet создаётся из CLI-аргументов без наследования предыдущего состояния. Неуказанные `--pending-check` и `--blocker` становятся пустыми массивами. Старые файлы остаются, но resume выбирает только последний.

**Воспроизведение:** checkpoint с незавершённой проверкой и блокером → следующий checkpoint того же assignment без повторения этих аргументов. В последнем packet оба массива пусты; `safeToContinue` меняется с false на true без разрешения блокера.

**Последствие:** частично потерянный контекст превращается в устойчиво сохранённую потерю информации при следующем checkpoint.

**Исправление:** наследовать состояние; операции добавления и снятия выполнять явно, с ID проверки/блокера и основанием снятия. Закрытие задания должно отвергать неразрешённые элементы. Для защиты от конкурирующих checkpoint использовать предыдущий packet ID/digest.

### F3 — P1: audit-time checks не связаны с фактическим запуском

**Источник:** [validate-closure-audit.py](../vibe-acceptance-auditor/scripts/validate-closure-audit.py), строки 83–100.

Проверяются поля `audit.checks`: argv, timestamps, fingerprints, executionStatus, exitCode и coverage. Но нет обязательной ссылки и хеша на receipt/log конкретной команды и проверки совпадения с записью runner. Host event подтверждает запуск аудитора, а не исполнение каждой заявленной им проверки.

**Воспроизведение:** в положительной фикстуре `audit.checks[0].argv` заменён на `command-that-was-never-run --fictional`. Валидатор аудита по-прежнему вернул `errors=[]`.

**Последствие:** ошибочное воспоминание или выдуманная запись аудитора структурно неотличимы от выполненной проверки. Это не доказательство злонамеренной подделки в реальных сессиях; это пробел в проверке происхождения evidence.

**Исправление:** обязательные `receiptRef`/SHA-256, log hash, точное совпадение argv, времени, fingerprint и coverage с runner receipt. Не принимать inline self-report как единственный источник результата команды.

### F4 — P2: возвращённое задание разрешается продолжать

**Источник:** [specialist-state.py](../vibe-developer/scripts/specialist-state.py), строки 44–52.

`resume` не учитывает `status=returned` в вычислении `safeToContinue`.

**Воспроизведение:** checkpoint с `--status returned`, затем resume: `status=returned`, `safeToContinue=true`, старый next action возвращён как действие продолжения.

**Последствие:** после сжатия специалист может повторно выполнять уже переданную работу. Оркестратор фильтрует такие packets, но прямой specialist resume — нет.

**Исправление:** returned должен быть терминальным состоянием с отдельным результатом «задание завершено»; возобновление — только через новое или явно переоткрытое назначение.

### F5 — P2: оркестратор может работать без сохранённого запроса и обязательной прозы

**Источник:** [checkpoint-delivery.py](../vibe-developer/scripts/checkpoint-delivery.py), необязательный `--required-read`; [resume-delivery.py](../vibe-developer/scripts/resume-delivery.py), строки 168–172.

Можно начать AC, не сохранив durable request и `execution.requiredReads`. Resume по умолчанию возвращает JSON спеки, ledger, FLOW/SCREEN и решения; product/domain/data/design/quality prose и необходимые specialist contracts автоматически туда не включаются. Обязательность их повторного чтения остаётся в инструкциях.

**Воспроизведение:** обычный `case.start()` без `--required-read`: `safeToContinue=true`, `savedRequiredReads=null`; пять нормативных Markdown-документов отсутствуют в списке required reads.

**Последствие:** список восстановления позволяет вернуть локальный AC, но не гарантирует восстановление сквозных ограничений и первоначального задания.

**Исправление:** до начала реализации требовать сохранённый request; строить обязательные чтения из зависимостей активного задания и нормативных контрактов, проверять наличие/хеши. Не полагаться только на вручную заполненный список.

## Ограничения, не сводящиеся к одному багу

**Сжатие не запускает recovery автоматически.** [recovery-contract.md](../vibe-developer/references/recovery-contract.md), строка 3, прямо говорит, что это правило workflow, а не host compaction hook. Это честная граница гарантии. Сохранённое состояние помогает только при своевременной записи и фактическом вызове resume. Приоритет — обязательный preflight в управляемых entrypoints и материальные checkpoints на границах операций; интеграцию с событиями хоста вводить только при реально доступной поддержке.

**Полнота прозы остаётся семантической задачей аудитора.** [audit_evidence.py](../vibe-developer/scripts/audit_evidence.py), строки 8–40, проверяет покрытие заголовков и корректность ID. Он принимает любое непустое объяснение `classification=context`. Проба, классифицирующая все разделы как context, прошла эту проверку. Это не означает, что реальный аудитор так поступит; означает, что machine validation не доказывает отсутствие пропущенных требований. Canonical inventory общий и строится из JSON; независимость достигается новым чтением прозы агентом. Нужны негативные evals с требованием, присутствующим только в прозе, несколькими требованиями под одним заголовком и пропущенной failure/platform веткой.

**Сам длительный аудит имеет более слабое восстановление.** Аудитор должен заморозить shadow inventory до чтения ledger, но формат промежуточного сохранённого inventory/progress не определён. Его read-only boundary не предусматривает recovery packets аудитора. Для больших AppSpec стоит разрешить отдельные immutable audit checkpoints с fingerprint и отметкой стадии; финальный audit оставлять отдельным неизменяемым результатом.

**Доказательство устойчивости к длинным сессиям пока узкое.** [stateful_evals.py](../vibe-developer/tests/stateful_evals.py) проверяет два свежих процесса на маленькой ValueStore-фикстуре с заранее сохранённым заданием и подсказками о восстановлении. Это полезный тест потери истории, но не повторные сжатия внутри длинной задачи. Grade проверяет факт resume-команды, а не обязательно её выполнение до первого редактирования. Agent evals запускаются только с `-IncludeAgentEvals`; launcher unit tests используют mock процесса.

В локальной `.tooling` найдены прежние результаты: две успешные фазы `cli-stateful-eval-full-20260906`, неудача `assets-2.2-stateful-eval` с `unfinished work was not checkpointed` и успешный retry. Это исторические артефакты, а не новая оценка текущей версии или статистика надёжности.

## Проверка и следующий порядок работы

В этом аудите запущены и прошли **44 теста**: recovery hardening — 13, delivery protocol — 12, audit protocol — 12, AppSpec — 5, audit runner — 2. Дополнительно выполнены описанные выше контрпримеры в временной Git-фикстуре. Исходные skills и тесты не изменялись; фикстура удалена после проверки.

Локальные артефакты воспроизведения: [.tooling/audit-20260906/reproduce.py](../.tooling/audit-20260906/reproduce.py) и [results.json](../.tooling/audit-20260906/results.json). Они находятся в игнорируемой `.tooling` и автоматически в Git не попадут. Реальные новые agent/compaction evals в рамках этого аудита не запускались.

Рекомендуемый порядок:

1. Закрыть F1–F3 и добавить regression tests с отрицательным результатом для текущего поведения.
2. Исправить F4–F5 и ввести проверяемые обязательные recovery-входы.
3. Расширить agent evals: несколько потерь контекста, новая инструкция пользователя посреди задания, неуспешная проверка, неполный hand-off, returned assignment, spec revision и требования только в прозе. Проверять реальные артефакты и порядок действий.
4. Добавить восстановление прогресса независимого аудитора и только затем оценивать надёжность на крупной AppSpec/длинной сессии.

Критерий успеха: после потери разговора агент восстанавливает первоначальный scope и новые решения, не забывает ни одно незавершённое обязательство, не повторяет возвращённые задания, а ни один путь финальной проверки не допускает завершение при непринятом результате или недоказанной проверке.
