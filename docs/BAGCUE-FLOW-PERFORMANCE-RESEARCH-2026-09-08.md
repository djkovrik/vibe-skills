# BagCue: длительность delivery flow и оптимизация

Исследование 8 сентября 2026. Код BagCue, его AppSpec и скиллы не изменялись. Это исследование процесса, а не независимый acceptance audit приложения.

## Вывод

Главная подтверждённая причина — слишком мелкая единица выполнения в сочетании с глобальной привязкой handoff/receipts к workspace. Это превращает специалистов в последовательную цепочку с многократной упаковкой результатов. Дополнительные причины: поздняя интеграция UI, повторяющиеся ошибки тестов/сборки и реализация миграций промежуточной схемы. Гипотеза о Sol Medium остаётся возможным усилителем, но сравнительного эксперимента нет.

Сокращение частоты screenshot tests само по себе этот запуск не ускорило бы существенно: до остановки нет Paparazzi record/verify receipts и нет golden PNG. Основная задержка произошла раньше.

## Как устроен текущий процесс

1. Approved AppSpec 2.0 → validation → canonical inventory → durable request → ledger/checkpoint.
2. Один активный AC, его владелец, исходный fingerprint и файловые границы.
3. По очереди необходимые роли: domain → persistence/network/platform → Decompose/MVIKotlin → UI/ресурсы → тесты.
4. Специалист читает профильные контракты, сохраняет assignment/recovery, реализует код и тесты, но Gradle не запускает. Возвращает immutable JSON с evidence и requestedCommands.
5. Оркестратор проверяет diff, импортирует handoff, запускает Gradle, передаёт ошибки владельцу. После исправлений повторяются проверка, упаковка и приёмка.
6. Все поверхности AC должны иметь актуальные receipts для одного workspace fingerprint, затем AC получает verified.
7. После всех AC — repository/platform/release gates, свежий независимый audit в отдельном процессе, затем ещё один covering final receipt и aggregate validation.

Роли и архитектурные контракты полезны: Domain — инварианты; Persistence — SQL/settings; Decompose и MVIKotlin — публичный компонент, состояние и события; Platform/Network/Monetization — внешние границы; Product Designer/Assets/Compose/Visual — экран и визуальные доказательства; Test — поведение; Architect — сборка/CI; Auditor — независимая полнота. Sync для BagCue без аккаунта и синхронизации не нужен. Проблема возникает при превращении каждого небольшого шага каждой роли в отдельную передачу управления.

## Подтверждённые причины

### 1. Глобальный fingerprint противоречит независимым владельцам файлов

`vibe-developer/scripts/ingest-handoff.py`:

- строки 43–45 требуют, чтобы changedFiles совпадал со всем drift от base до текущего workspace;
- строки 46–47 требуют совпадения result fingerprint со всем текущим workspace;
- внутри `mutate` base fingerprint должен совпасть с baseline всего AC.

Следовательно, специалист B после специалиста A не может просто предъявить свой локальный delta от начала своей работы. Он вынужден учитывать накопленный drift всего AC. Независимое изменение другого файла делает готовый handoff stale. `compute_workspace_fingerprint` включает HEAD, общий diff и изменённые/untracked файлы; `docs/assignments` также входит в fingerprint. Исключения для `.vibe` evidence и generated reports уже существуют, но этого недостаточно.

Это не только потенциальный риск. В сообщениях основного агента:

- 07.09 20:37 МСК: persistence handoff отклонён из-за baseline специалиста вместо baseline AC-001; запрошена коррекция метаданных без изменения production.
- 21:50: такая же проблема на AC-003.
- 08.09 01:13: готовый component-код AC-009 ждёт расширения ledger на 16 путей.
- 04:44: Compose сознательно не меняется, пока проходит cumulative handoff ассетов.
- 04:59: component correction отклонён как stale из-за параллельных Compose-правок.

Агент неоднократно прямо пишет, что запрещает параллельные записи ради fingerprint. Таким образом, многoагентность используется в основном для read-only подготовки, а критический путь остаётся последовательным.

### 2. AC стал единицей планирования, хотя должен быть единицей приёмки

AC-002 «создать предмет» и AC-003 «редактировать предмет» выполнялись отдельными полными циклами. AC-006…010 аналогично дробят один template editor/list flow. На уже существующей основе каждый такой цикл занимает примерно 19–31 минут; AC-004 — 36 минут, AC-006 и AC-012 — около часа.

Примерные интервалы из ledger, с округлением:

| Работа | Длительность |
|---|---:|
| Старт и подготовка до AC-001 | 47 мин |
| AC-001, основа domain/data/component | 83 мин |
| AC-002…005 | 96 мин |
| AC-006…010 | 179 мин |
| AC-011…013 | 107 мин |
| AC-014 до остановки | 111 мин |

Здесь длительности группы считаются от начала первого AC до последнего обновления последнего; они включают переходы и сопутствующие работы. Часть общей архитектуры строилась внутри первых AC, поэтому линейно экстраполировать время на остальные 37 нельзя.

### 3. «Verified» не означал подключённый пользовательский флоу

AC-001…013 требуют главным образом component/domain/persistence evidence. Формально их можно проверить без Compose и production navigation. Первый golden-test появляется в AC-014 и вытягивает поздний большой пакет: дизайн, ассеты, UI, 32 previews и scanner/Paparazzi.

В текущем `androidApp/.../AppActivity.kt:19` вызывается `App`, а `shared/compose/.../App.kt` всё ещё содержит Cyclone demo. Реализованный ActiveSessionScreen пока не заменил production entry point. В Compose есть только экран активной сессии, его previews и theme; остальные основные экраны не реализованы как законченный UI.

Поэтому 13/51 = 25,5% — только доля ledger-статусов, не процент готовности. Домен, БД и компоненты представляют существенный полезный результат, но до финиша действительно далеко: навигация, остальные экраны, reminders, analytics/privacy/ads, визуальные проверки и gates ещё требуют работы. Точное оставшееся время без дополнительного delivery-планирования неизвестно.

### 4. Повторные проверки вызываются изменением нерелевантного кода

В сообщениях на AC-001, AC-004, AC-006 прямо указано: успешный persistence receipt повторяется после component-правок ради общего fingerprint. В receipts database host tests фигурируют 29 раз, template component allTests — 26 раз, migration verification — 13 раз.

`validate-delivery-ledger.py:83` и далее отбрасывает evidence с несовпадающим workspace fingerprint. Это хорошая строгость для окончательного release snapshot, но слишком грубая зависимость для промежуточного domain/persistence теста. Сейчас новый assignment-документ и правка независимого UI способны устарить одинаковый тест БД.

### 5. Ошибки реальны, но feedback loop слишком длинный

36 неуспешных receipts не равны 36 дефектам продукта: есть проблемы доступа к Gradle cache, передачи массива tasks, source-set/build API и ошибки тестовых fixtures.

Повторялись, в частности:

- Kotlin type inference в component tests AC-002/003/004/006/014;
- асинхронный cancel/output в template tests AC-008;
- SQLite driver/transaction fixtures на AC-011 и AC-012;
- `JvmInline` common/iOS compilation, generated SQL API, отсутствующая coroutine dependency;
- Compose theme-local вне composable context.

Цикл «статически готово → immutable handoff → приёмка → первая компиляция → отправка обратно → новый handoff» поздно даёт специалисту самую дешёвую обратную связь. Одна и та же категория ошибки воспроизводится в следующих AC. Это поддерживает гипотезу о недостаточной адаптации агента, но не доказывает, что виновато именно Medium.

### 6. Промежуточные миграции увеличили объём работы

Есть создание v1 schema snapshot перед template-расширением и upgrade/legacy-localization fixtures уже в первой разработке приложения. В `data.md:137` написано: каждый schema change требует numbered migration, upgrade tests — от shipped schemas. Поэтому нельзя считать сделанные миграции самовольными: текст действительно толкает к этому процессу. Но для будущего greenfield-проекта стоит явно различать evolving initial schema и уже поставленную пользователям схему. Это изменение политики требует согласованного обновления спецификации, а не удаления текущих миграций BagCue.

## Насколько виновата модель

Основной агент и все 11 непосредственно порождённых специалистов использовали `gpt-5.6-sol`, `medium` — подтверждено turn_context. Нет данных о сравнении этого же AppSpec на другой модели/effort и нет сопоставимых замеров прежних приложений до одинакового критерия завершения.

Официальная страница [GPT-5.6 Sol](https://developers.openai.com/api/docs/models/gpt-5.6-sol) описывает Sol как flagship для сложной профессиональной работы и Medium как default reasoning effort. Это не гарантия скорости или качества конкретного KMP-проекта. Документация не позволяет приписать этому запуску определённый процент замедления из-за Medium.

Историческое сравнение правил гораздо определённее: diff от `a6ba0dc` добавляет Protocol 2.0 ledger, обязательные immutable handoffs/recovery для специалистов, глобальные fingerprints, fresh audit и final receipt. При этом Store/Manager, M3, previews/goldens и последовательный Lazyweb review уже существовали в прежнем процессе. Поэтому новая административная механика — более сильное объяснение регрессии, чем сам факт наличия архитектурных контрактов или screenshot tests.

Рабочая гипотеза для проверки: оставить Sol Medium на ограниченных реализациях, сравнить Sol High на планировании пакета, сложных межслойных контрактах и повторных сбоях. Не переключать весь запуск на максимальное effort вслепую: дополнительное рассуждение само имеет стоимость, а ошибки протокола останутся при любой модели.

## Предлагаемый процесс

### P0: единица выполнения — законченный capability/flow с несколькими AC

Сохранить все 51 AC как независимые обязательства, но планировать работу пакетами:

- catalog: AC-001…005;
- templates: AC-006…011;
- session creation/merge: AC-012…018;
- packing/completion: AC-019…025;
- history: AC-026…030;
- reminders: AC-031…035;
- analytics: AC-036…039;
- privacy/ads: AC-040…046;
- cross-cutting acceptance: AC-047…051 проверяется по мере затронутых флоу и финально.

Это ориентир, не требование назначать огромный пакет одному агенту. Дробить по зависимостям и риску; ключевое — не повторять полный ритуал для create/read/update одного редактора. Один handoff/receipt может покрывать несколько AC, но только с реальным evidence по каждой поверхности.

Добавить ранний интеграционный milestone: запущенное Android-приложение открывает реальный root, каталог/редактор, сохраняет данные и восстанавливает их после перезапуска. Затем каждый пакет подключается к этому root. Статус component-verified не выдавать за завершённый пользовательский флоу.

### P0: отделить assignment evidence от глобального closure snapshot

Для handoff хранить baseline конкретного assignment, authored delta, хеши принадлежащих ему файлов и входных контрактов. Оркестратор отдельно объединяет результаты в AC. Изменение чужого непересекающегося файла не должно автоматически требовать новый handoff.

Для targeted receipts использовать набор входов проверки: production/test sources соответствующих модулей, транзитивные зависимости, build logic, toolchain, resources и значимые spec-контракты. Если полноту набора установить нельзя — консервативно расширять область или выполнять полную проверку. Глобальный snapshot, immutable evidence и независимый audit сохранить для финального завершения.

Не просто удалить fingerprint validation: тогда потеряется защита от реального stale evidence. Нужна новая семантика области действия и тесты на изменение собственного файла, зависимого контракта, общего build logic и нерелевантной документации.

### P0: компиляция до окончательного handoff

Оставить один сериализованный Gradle runner/очередь. Специалист должен уметь запросить compile/targeted test в состоянии «реализация готова к проверке», получить receipt и исправить дефект до final handoff. Root остаётся владельцем запуска; формальную передачу результата не делать предусловием первого compile.

Автоматизировать capture baseline, создание handoff, ingest+checkpoint и привязку receipt. Команды принимать через JSON request file, чтобы не собирать длинные PowerShell argv и cumulative changedFiles вручную. Новые handoffs создавать для реальных новых результатов, а не для перепечатывания глобального fingerprint.

### P1: проверять на трёх уровнях

| Этап | Проверка |
|---|---|
| Во время реализации | Compile изменённых модулей, тест нового поведения, затронутые регрессии |
| На завершении capability | Совместная domain/component/persistence проверка; подключённый UI; targeted previews/goldens |
| Интеграционный/final milestone | Полная матрица, quality/build gates, macOS iOS checks, fresh acceptance audit |

Повторный запуск после исправления — только затронутая матрица, если остальная evidence остаётся валидной по зависимостям. Последовательный Gradle нужен; последовательные непересекающиеся source edits ради общего хеша — нет.

### P1: screenshot cadence и Lazyweb

- Scanner/Paparazzi инфраструктуру один раз проверить на небольшом production smoke-preview в начале, чтобы не обнаруживать несовместимость host/source sets на первом большом экране.
- На каждую UI-правку компилировать previews; record/inspect/verify делать на стабилизировавшемся экране или capability, затем только для затронутых снимков.
- Сохранять все основные состояния в light/dark. Stress-варианты выбирать по риску/pairwise: текущий preview-contract уже разрешает это, полный декартов набор не требуется.
- Сохранять Lazyweb research до проектирования и один полный последовательный review стабильных экранов. Повторять review при существенном изменении экрана или для закрытия finding, а не после каждого AC.
- Правило одного Lazyweb report в работе сохранить: это ранее явно заданное пользователем ограничение. Остальная независимая работа может продолжаться во время ожидания отчёта.
- Требования golden-test не исчезают из AC. До визуальной проверки такой AC остаётся implemented-unverified, а следующая независимая работа может продолжаться.

### P1: компактный recovery и ограничение повторных попыток

Вместо полных fingerprint objects во многих артефактах хранить ссылки на один immutable snapshot. Resume должен выдавать компактный active package, pending checks, blockers и next action, а не полную историю. Контракты читать один раз на неизменную revision и повторно только при изменении/восстановлении утраченного контекста.

Checkpoint оставить на начале assignment, существенном результате, перед передачей/прерыванием и после завершения пакета. Автоматические checkpoints во время работы допустимы; они не должны требовать отдельного рассуждения агента для каждого расширения списка файлов. Границы задавать разумными feature globs, а не угадывать каждое будущее имя файла.

После второго одинакового сбоя остановить тот же repair loop: классифицировать источник, подготовить минимальный воспроизводимый случай и при необходимости поднять effort/передать ограниченную диагностику. Исправленный test harness/pattern распространять на следующие AC, чтобы type-inference и SQLite fixture ошибки не повторялись.

### P2: greenfield и финальная проверка

В шаблоне AppSpec явно разрешить изменение initial schema до первого опубликованного baseline; после выпуска — строгие миграции и upgrade tests. Для BagCue текущая frozen spec сохраняется до принятия изменения пользователем.

Проверить необходимость трёх полных прогонов «pre-audit → audit-time → after-audit final». Предпочтительная будущая схема: один финальный integration run на замороженном состоянии, fresh auditor читает receipts и независимо выполняет необходимые контрольные проверки, после PASS выполняется лёгкая проверка неизменности и агрегирование. При изменении кода проверки повторяются. Это потребует изменения validator/schema/contracts; текущий протокол так завершать не разрешает.

## Как проверить эффект

Сначала исправлять P0, затем измерять, а не обещать ускорение в несколько раз без эксперимента. Нужны одинаковые starting snapshots, требования и критерий завершения для сравнения.

Метрики на пакет: wall-clock до работающего flow, число model/tool calls, время команд, first-pass compile/test success, corrective handoffs только из-за метаданных, повторы тестов без изменения их входов, количество AC с текущей evidence и число реально подключённых экранов. Ожидания агентов и время выполнения учитывать отдельно и не складывать перекрывающиеся интервалы.
